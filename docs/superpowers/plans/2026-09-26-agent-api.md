# Agent API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let agents use account-owned API keys and a documented REST API to manage Shelf boards, categories, assignments, apps, and icons.

**Architecture:** Better Auth manages user-owned keys. Hono with `@hono/zod-openapi` exposes `/api/v1`, validates requests, and generates its contract. REST and tRPC call shared server operations; the REST layer resolves a key to a user and formats HTTP responses.

**Tech Stack:** Next.js App Router, Better Auth API Key plugin, Hono, `@hono/zod-openapi`, Zod 4, Prisma/SQLite, Vitest.

**Spec:** `spec/agent-api.md`; also follow `spec/architecture.md`, `spec/accounts.md`, `spec/apps-and-icons.md`, `spec/boards.md`, and `spec/categories.md` for shared behavior.

## Global Constraints

- The API base is `/api/v1`; only `GET /api/v1/openapi.json` is public. Data routes require `Authorization: Bearer <key>` and ignore browser cookies.
- A key has full shared-app access and access only to its owner's boards. Keys have no scopes and do not expire by default.
- Keep existing tRPC procedure names, input/output behavior, and browser sessions. Reuse business operations and existing validation and icon-cache rules.
- All new npm dependencies use the `latest` tag at installation time; commit the lockfile and Prisma migration. Persist keys in `/data/app.db` through the existing startup migration path.
- Responses and error codes follow `spec/agent-api.md`; save a generated OpenAPI copy at `spec/openapi.json` and check it against the served document.
- Do not launch implementation now. Tomorrow, work in **no more than four Herdr tabs and four total agents**: one coordinator and at most three implementers. The coordinator integrates reviewed commits. Give each implementer an isolated worktree/branch; do not share an editable checkout. Keep the tabs until PR feedback is resolved.

## Review Focus

1. A cookie without a bearer key gets `401`, even for a signed-in user (Task 3 test).
2. A revoked key fails on its next request while another key for that user still works (Task 1 and Task 3 tests).
3. A foreign board is hidden with `404`, and a category from another board is rejected with `400` (Task 5 test).
4. Duplicate assignment returns `409`, and incomplete or cross-group order lists return `400` without changing order (Task 5 test).
5. A failed, non-PNG, or oversized icon download returns a retryable error and leaves the app unchanged (Task 4 test).

### Task 2: Shared board operations and ordering

**Files:** Create `src/server/board-operations.ts` and `src/server/board-operations.test.ts`; modify `src/server/routers/board.ts`; retain `src/server/board-service.ts` for existing order helpers.

**Interfaces:** Export `boardOperations` with `list(userId)`, `get(userId, boardId)`, `create(userId, name)`, `rename(userId, boardId, name)`, `delete(userId, boardId)`, `setDefault(userId, boardId)`, `assign(userId, boardId, appId, categoryId)`, `unassign(userId, boardId, appId)`, `moveApp(userId, boardId, appId, direction)`, `setAssignmentCategory(userId, boardId, appId, categoryId)`, `createCategory(userId, boardId, title, description)`, `updateCategory(userId, boardId, categoryId, title, description)`, `deleteCategory(userId, boardId, categoryId)`, `moveCategory(userId, boardId, categoryId, direction)`, `setCategoryOrder(userId, boardId, categoryIds)`, and `setAppOrder(userId, boardId, appIds)`. Existing methods preserve their tRPC result shapes; new exact-order methods return `void`. `get` and `list` include categories and assigned apps. Export `BoardOperationError` with `code: "NOT_FOUND" | "BAD_REQUEST" | "CONFLICT"`.

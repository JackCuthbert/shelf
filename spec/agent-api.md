# Agent API

Shelf exposes a small JSON REST API for agents and other HTTP clients. A signed-in user creates an API key on `/account`, gives it to the client, and uses the published OpenAPI document to discover requests. The key acts as that user: it can manage all of their boards and the shared app library. It has no separate scopes or read-only mode.

## Implementation boundary

- `/api/v1` is the versioned REST base path. [Hono](https://hono.dev/docs/getting-started/nextjs) runs inside the existing Next.js Node.js application. [`@hono/zod-openapi`](https://hono.dev/examples/zod-openapi) validates requests and generates the OpenAPI document from the route definitions; the document is served at `GET /api/v1/openapi.json` without authentication. Commit a generated copy to `spec/openapi.json` when implementing the API and check that it matches the served document. Do not hand-maintain a second contract.
- [Better Auth's API Key plugin](https://better-auth.com/docs/plugins/api-key) owns key generation, hashing, lookup, listing, and revocation. The account page uses its session-authenticated operations. Configure user-owned, named keys, with no custom permissions, no expiration by default, and no client-selected key prefix or metadata. Show the plaintext key only in the creation result. The account page lists each key's name, creation date, and last-used date when available, and can revoke it with confirmation. Revocation takes effect on the next request. Signing out or changing the account password does not revoke API keys; deleting the account does.
- REST handlers accept only `Authorization: Bearer <key>`. A browser session cookie does not authenticate `/api/v1` data operations. Verify the key through Better Auth and resolve its owning user before handling a protected request. Never put keys in URLs, responses after creation, or logs. Every data operation enforces the same board ownership rule as the UI; a key cannot edit or list another account's boards. Every authenticated user can read and write the shared app library. There are no per-key permission checks.
- REST and tRPC call the same server-side board, app, category, ordering, and icon operations and use the same validation rules. Extract the board operations currently embedded in tRPC procedures as needed; do not duplicate business rules in Hono handlers. Keep the existing browser routes and session behavior.

## Resource contract

All IDs below are stable database IDs. A board response also includes its public `nanoid` and `/board/<nanoid>` URL. Successful writes return the resulting resource, except deletes, which return `204 No Content`. Lists have a stable order: boards by creation time then ID, apps by name then ID, categories by saved position, and assignments in display group and saved order. Dates are ISO 8601 strings. App responses expose the saved icon source, slug or custom URL, local icon URL, description, and recorded liveness state.

| Method                     | Path                                        | Behavior                                                                                                                                                                                                     |
| -------------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET` / `POST`             | `/boards`                                   | List the key owner's boards with categories and assignments / create a board with `name`. The first board becomes default.                                                                                   |
| `GET` / `PATCH` / `DELETE` | `/boards/{boardId}`                         | Read one owned board / rename with `name` / delete it. Deleting the default selects the oldest remaining owned board.                                                                                        |
| `PUT`                      | `/boards/{boardId}/default`                 | Set an owned board as the user's default.                                                                                                                                                                    |
| `GET` / `POST`             | `/apps`                                     | List all shared apps / create one.                                                                                                                                                                           |
| `GET` / `PUT` / `DELETE`   | `/apps/{appId}`                             | Read one shared app / replace its editable fields / delete it and all board assignments.                                                                                                                     |
| `POST`                     | `/boards/{boardId}/categories`              | Create a category with `title` and optional `description`.                                                                                                                                                   |
| `PATCH` / `DELETE`         | `/boards/{boardId}/categories/{categoryId}` | Edit title and/or description / delete the category, moving its apps to the end of uncategorized apps.                                                                                                       |
| `PUT`                      | `/boards/{boardId}/categories/order`        | Set category order with `categoryIds`, a complete permutation of that board's category IDs.                                                                                                                  |
| `POST`                     | `/boards/{boardId}/apps`                    | Assign an existing shared app with `appId` and optional `categoryId`; omitted or `null` means uncategorized.                                                                                                 |
| `PATCH` / `DELETE`         | `/boards/{boardId}/apps/{appId}`            | Set `categoryId` to another category on this board or `null` / remove the assignment without deleting the shared app. Changing category appends the app to its new group.                                    |
| `PUT`                      | `/boards/{boardId}/apps/order`              | Set assignment order with `appIds`, a complete permutation of assigned app IDs in display group order: uncategorized first, then each category in its saved order. Category membership is unchanged.         |
| `GET`                      | `/icons/search?q={query}&limit={limit}`     | Search published Dashboard Icons slugs and aliases. Return matching `slug`, `aliases`, and remote `previewUrl` values in deterministic slug order. Query is required; default limit is 20 and maximum is 60. |

The `POST /apps` and `PUT /apps/{appId}` bodies contain the complete editable app fields: `name`, `description` (empty string allowed), `url`, and exactly one icon choice. A Dashboard Icons choice is `{ "iconSource": "dashboard", "iconSlug": "..." }`; a custom PNG choice is `{ "iconSource": "url", "iconUrl": "https://..." }`. The app response uses `customIconUrl` for a saved URL and includes `iconHash` when applicable. `PUT` requires all editable fields, even when only one changes, so switching icon sources is explicit. Server-managed IDs, assignments, status, and timestamps cannot be set through these bodies.

All existing app, board, and category limits apply. App and custom icon URLs accept HTTP(S), including private household hosts. Saving an icon slug validates it and caches its PNG; saving a custom icon URL downloads and verifies a PNG of at most 5 MB, hashes its bytes, and reuses an identical cached file. App creation or replacement commits only after a new icon has been cached successfully. An unchanged custom icon URL is not downloaded again. Unreferenced cached icons are cleaned up under the existing rules. Icon search only reads the remote catalogue and does not save previews or catalogue data to `/data`.

## Responses and failures

- Every protected request without a valid, active bearer key returns `401` with `{ "error": { "code": "UNAUTHORIZED", "message": "..." } }`. Missing resources and boards owned by someone else both return `404`.
- Invalid JSON, missing fields, invalid URLs, invalid category membership, and incomplete or invalid order lists return `400`, with field-level details where applicable. A duplicate board assignment or case-insensitive duplicate category title returns `409`. A remote icon catalogue or PNG fetch failure returns `502`; the app remains unchanged. Unexpected failures return `500` without exposing secrets or internal details.
- Create operations return `201`; reads and edits return `200`; deletes return `204`. Responses use `application/json` except `204`. The OpenAPI document defines concrete schemas, status codes, bearer security, and examples for every operation.
- No anonymous board listing is added. Existing public `/board/<nanoid>` pages remain separate from this API.

## Acceptance checks

- A user creates two named keys on `/account`, sees each plaintext value once, uses either for read and write operations, and can revoke one without affecting the other or a browser session.
- A key can manage the shared app library and its owner's boards, categories, default board, assignments, and ordering. It cannot list or mutate another user's boards. An invalid or revoked key cannot access protected endpoints.
- An agent can search icons, choose a slug or custom PNG URL, and create or edit an app. Search does not persist icons; a failed download leaves the app unchanged.
- Duplicate assignments, invalid cross-board categories, incomplete order lists, and deletion side effects follow the existing board and app rules.
- The served OpenAPI document matches the generated checked-in copy and describes requests, responses, errors, and authentication for every endpoint. A documented HTTP example can create a board, create an app, assign it, and read the resulting board.
